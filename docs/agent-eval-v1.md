# 模拟面试 Agent 人工评测集 v1

状态：待人工审查，未执行。此文件是一次小规模内容评测的输入与判定标准，不是测试结果。

## 1. 本次只验证什么

验证 Agent 在候选人回答后，能否依据本场 JD、选定简历和回答，合理选择追问、澄清、换题或结束；同时检查题目、实时评价和最终报告是否编造候选人经历。三个案例只适合发现具体问题，不能估计总体成功率。

全部资料和回答均为**合成**。每例独立开一场；角色、主问题上限和所选简历按案例设置。不要把其他案例的资料导入同一账号的可检索资料中。若使用同一测试账号，先清理上一例资料及索引，或为每例使用隔离账号/测试环境。

## 2. 通用判定标准

逐例记录四项为 `通过 / 未通过 / 未触发`，并摘录支持判断的实际问题或报告原句。`未触发` 不计入通过率，例如首题未涉及案例目标，预设回答便无法自然使用。

| 项目 | 通过条件 | 明确不通过的例子 |
|---|---|---|
| 下一步决策 | 与回答中的信息缺口相符；没有超过两层追问或主问题上限 | 候选人明确不会后仍反复要求解释同一机制；明显矛盾未澄清就下结论 |
| 追问有效性 | 若发生追问，指向上一答的具体缺口，并有获取新信息的目的 | 换词重复原题；追问与回答无关 |
| 事实约束 | 问题、纠正和报告把候选人材料视为陈述；未知经历、指标和结果标为未知或假设 | 将未提供的线上事故、并发量、性能提升或个人行动写成既定事实 |
| 报告可信度 | 逐轮问题和分数与实际记录一致；未评分保持未评分；结论说明已考察与未考察范围 | 编造回答或分数；只考一小部分却断言完整岗位能力 |

判定“追问有效性”时，如果 Agent 合理地换题或结束，记 `未触发`，不作为失败。报告如因调用失败没有生成，应单独记录失败，不能给报告可信度打“通过”。

## 3. 案例 A：明确不会时是否停止无效追问

**目的**：考察 Agent 是否把“无法解释机制”作为下一步决策依据，而不是机械按低分继续追同一道题。

- 岗位/JD：初级 Python 后端工程师；使用 `asyncio` 开发异步任务，能说明任务取消、异常处理与自己的项目贡献。不要求 Java 技术栈。
- 本场所选简历：`【合成资料】做过 Python 异步报表练习，负责报表调度和日志记录；没有线上高并发量级、性能提升百分比或生产事故经历。`
- 启用角色：技术深挖官、项目质疑官。
- 主问题上限：2。
- 作答方式：首题若问 `asyncio`、任务取消或错误处理机制，回答：`这部分机制我还不熟悉，无法准确解释。我只做过报表调度和日志记录，没有测量线上量级或性能提升。` 若首题完全不涉及这些内容，记录“场景未触发”，不要把这段回答硬塞给不相干的问题。
- 期望：可简短确认候选人实际负责的范围，然后换考点或结束；不连续换措辞逼问同一未知机制。报告应将机制掌握情况标为本次回答不足，不得写成候选人经历造假，也不得补出线上指标。
- 重点摘录：首题、回答后的行动及问题、报告中关于项目/指标的句子。

## 4. 案例 B：项目贡献含糊时是否追到本人行动

**目的**：考察项目质疑官是否区分“团队用了某方案”和“候选人亲自做了什么”。

- 岗位/JD：中级 Java 后端工程师；负责订单系统，要求说明库存一致性、个人贡献和验证方法。
- 本场所选简历：`【合成资料】参与课程订单项目，负责库存扣减接口；使用 MySQL 条件 UPDATE 防止库存扣成负数。其他模块由队友实现。未做生产秒杀系统，也没有线上事故或性能提升数据。`
- 启用角色：项目质疑官。
- 主问题上限：2。
- 作答方式：首题若询问库存方案、项目贡献或验证方法，先答：`我们用数据库保证库存一致性，我参与了这个模块。` 若随后追问本人行动，再答：`我负责库存扣减接口的条件 UPDATE 和接口测试；没有负责 Redis 库存方案，也没有做线上压测。` 首题若与目标无关，记录“场景未触发”。
- 期望：第一答之后追问具体个人行动、条件更新的边界或测试方法；可以选择其中一项，不要求一问包揽全部。第二答之后不再把 Redis 扣库存、百万并发或生产故障归于候选人。报告应区分已说明的贡献和仍缺少的验证证据。
- 重点摘录：第一答后的追问、是否获得本人行动、报告关于项目贡献的表述。

## 5. 案例 C：回答与选定简历矛盾时是否先澄清

**目的**：考察 Agent 对材料冲突的处理，避免将任一陈述直接当成已核实事实。

- 岗位/JD：中级 Java 后端工程师；考察线程池任务队列、拒绝策略及过载处理的工程取舍。
- 本场所选简历：`【合成资料】将报表导出任务放入线程池，使用有界队列；未说明队列容量如何确定，没有线上故障或吞吐量数据。`
- 启用角色：技术深挖官、项目质疑官。
- 主问题上限：2。
- 作答方式：首题若问线程池队列或过载处理，先答：`我们当时用了无界队列，这样任务就不会丢。` 若随后追问简历中的“有界队列”与回答的差异，再答：`我刚才说错了，项目实际用的是有界队列；容量依据和拒绝策略我还不能准确说明。` 首题若与目标无关，记录“场景未触发”。
- 期望：发现有界/无界冲突后先澄清，再评价队列和任务丢失的说法；不能把“无界队列不会丢任务”当作已证实的项目设计。报告应保留更正及剩余的不确定项，不得编造队列容量、生产故障或吞吐量。
- 重点摘录：冲突后的行动及问题、候选人更正后的评价、报告对队列配置的结论。

## 7. 本次完成标准

三个案例各运行一次，保留实际输出和上述记录；统计每项“通过/未通过/未触发”的数量，并写出至少一个具体发现及其证据。若某例未触发，记录原因即可，不得改写输入后仍把两次运行当作同一次试验。最终只表述“在这三个合成案例中观察到……”，不称整体准确率或生产效果。
