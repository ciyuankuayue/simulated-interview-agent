# 模拟面试 Agent 评测实操记录（2026-11-03）

## 0. 先看结论

本次整理了可审查的 [3 例动态 Agent 评测集](../../agent-eval-v1.md)，并核对仓库中两批历史真实模型运行。今天第一次在默认执行环境启动隔离测试，因该环境无法解析模型域名而中止；随后在可联网环境**重新运行成功**，取得一条新的真实 Agent 合成案例。第一次运行不能判断是否发生外部 API 用量；成功结果只归于第二次运行。

能够如实使用的数字：历史首题测量为 **6 个独立合成场景、24 条正式请求（每种配置 12 条）**；两组均 12/12 成功生成非空首题。非思考配置本批 P50/P95 为 **874/1207 ms**，思考配置为 **991/2210 ms**。参与设计的 Codex 助手盲评达标数分别为 **12/12 与 10/12**，属于辅助评阅。今天的新动态 Agent 单案例测试 **1 项通过、0 失败、0 跳过**，产生两题（第二题未回答）及报告，记录 **5 次模型调用、11196 token**。这些数据来自不同目标的实验，**不能拼成“优化前后提升”**。

## 1. 问题、范围与评测集

业务问题：Agent 是否根据本场 JD、选定简历和回答决定追问、澄清、换题或结束，同时避免编造经历，并给出可信报告。

今天新增的 v1 评测集在 [agent-eval-v1.md](../../agent-eval-v1.md)：3 个独立合成案例，分别是“明确不会”“本人贡献含糊”“简历与回答冲突”；覆盖 Python 初级和 Java 中级、技术深挖官与项目质疑官。每例约定 JD、所选简历、预设回答、目标行为、触发条件和四项判定标准。**这 3 例尚未按文件配置逐一执行**；今天运行的是现有 `AgentLiveSmokeTest`，与案例 A 相似，但主问题上限设为 1，不能冒充 v1 案例 A 的正式结果。行为面试官和高级岗位未覆盖，是下一版应补的样本层。

历史首题实验是另一套固定输入：[6 个合成场景](../2026-10-20-first-question/cases.json)：中级 Java 后端 5 例（MySQL、Redis、线程池、库存项目、协作冲突），中级 Python 后端 1 例（asyncio）；角色是技术、项目、行为三类。每例两配置各重复两次，即 6×2×2=24 条正式请求，另有两条预热不纳入统计。**24 是请求数，独立场景只有 6 个**；没有高级、初级、前端等岗位，也没有完整多轮表现。输入、环境和源码版本记录在[历史 manifest](../2026-10-20-first-question/manifest.json)。

## 2. 指标与计算方法

| 指标 | 口径 | 本次证据状态 |
|---|---|---|
| 首题成功率 | HTTP 200 且首题非空 / 正式请求数；失败和超时保留在分母 | 历史实验可算，24/24；今天是服务层测试，非 HTTP 请求 |
| 首题响应时间 | 本机 HTTP 请求至完整首题响应；P50/P95 用 nearest-rank，即排序后取 `ceil(p×n)` 项 | 历史两组各 n=12，可算；不能代表整场或生产 P95 |
| 首题辅助质量 | 相关性、岗位适配、深度、证据约束各 0–2；总分≥6 且每项≥1 算达标 | 历史有盲评文件；评分者不独立 |
| 严重无依据经历 | 证据约束得 0 的题数 / 正式题数；需逐题保留原句和资料 | 历史思考组 2/12，非思考组 0/12；样本不足以推断总体差异 |
| JD 核心点覆盖率 | 事先列出的必考点中，整场实际有效考察的点数 / 必考点总数 | **未测**；首题实验的“相关性”不能替代整场覆盖率 |
| 个性化程度 | 固定同一 JD/级别/模型，仅改变候选人简历，比较问题针对材料的差异，并人工判断是否有意义 | **未测**；现有案例同时改变 JD，不能做归因 |
| 评分可靠性 | 同一回答由独立人工依据预定 rubric 评分，再比较模型分数（如平均绝对误差、分档一致率） | **未测**；历史 Codex 评的是首题质量，不是候选人回答分数 |
| 生成失败/重试成功 | 预先定义一次调用或完整场次的分母，逐次保留错误、重试和最终状态 | 历史首题样本 0/24 失败；今天第二次服务层测试 1/1 通过；不同环境的两次执行不能拿来计算生产重试成功率 |
| Multi-Agent vs Single-Agent | 同一批案例、模型和预算下，记录架构、调用数、token、成本、质量 | **未测**；仓库当前是一个受约束的面试决策 Agent 配合判分/Critic 职责，不能把它包装为已完成的多 Agent 对照实验 |

质量对照要先冻结输入、模型、评分规则和预算，再用同一批案例成对运行 A/B，隐藏配置标签给独立评审，报告每例差值及失败案例。只有“同样输入、只改一个变量”的结果才能谨慎讨论改动效果。历史实验只对比同一模型请求的思考开关，不是动态 Agent 重构前后对比，更不是多 Agent 对照。

## 5. 模型给自己打分的偏差怎么处理

本项目的 Critic 是**被评测系统的一部分**，它生成的分数、理由和报告只能作为“系统输出”，不能直接当评测真值。历史首题质量分来自参与设计的 Codex 助手，虽然先隐藏配置标签，仍有设计者偏差。对此本报告明确称“辅助评阅”，不称独立验证。

下一次正式质量对照应让至少两位不看配置标签的评审者，先按同一规则独立给候选人回答及报告评分；分歧保留并讨论，形成参考标注。再计算模型分数与参考标注的差值及分档一致率，并展示样本量和争议样本。若使用另一模型做裁判，先在已有人工作答的样本上验证其误判，不用它替代人工真值；不同模型也可能共享偏差。

## 6. 当前能讲与不能讲的项目结论

可讲：建立了有输入、期望行为和“未触发”规则的 Agent 评测集；历史首题真实请求支持“在 6 场景/24 请求的小样本里，非思考配置 P50 为 874 ms、思考配置 991 ms”；盲评定位了两条把候选人未提供经历写成事实的题。今天的动态 Agent 单案例真实测试通过，留有决策、两题、报告和 **5 次调用/11196 token** 的原始证据；第一次因默认环境 DNS 不通而中断，也如实保留。v1 三例尚未完整执行。

不能讲：完整面试质量提升百分比、岗位核心点覆盖率、个性化提升、评分与人工一致率、线上 P95、重试成功率、多 Agent 比单 Agent 的成本或质量优势。这些都没有同口径实测。

## 7. 换新评测场景时照此做

1. 定一个业务问题和可观察失败（例如“回答与简历冲突时先澄清”）。
2. 固定案例输入、触发条件、可接受行动和禁止行为；样本按岗位、职级、角色、资料完整度分层，并清楚区分独立案例数和重复请求数。
3. 在调用前写好通过条件、分母、未触发处理、预算和版本清单。
4. 先跑当前版本，保留全部成功、失败、超时、重试的原始输出与调用统计；失败不删样本。
5. 人工盲评，具体指出输入/输出片段；系统自身评分不算真值。
6. 只改一个主要变量，同案例成对复测，比较逐例差值、总体统计和成本；最后陈述样本量与未测范围。
