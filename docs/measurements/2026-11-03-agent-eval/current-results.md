|---|---:|---:|---|
| 首题真实模型 | 6 | 24 次 HTTP 请求，另有 2 次预热 | 24/24 返回 200 且非空；**测试最终失败**，因行为案例同例提示词哈希不一致 |

| RAG 检索 | 15 个主题 | 150 篇合成文档、30 条查询 | 测试 1/1 通过；向量 Recall@5 96.7%、MRR@10 0.825 |
| 多轮案例池 v2 | 12 个设计案例 | 其中 3 场与新增测试相似，但配置不同 | **没有按 v2 全量执行**；不能报 12 例通过率 |

这些不是同一批受试对象；不能把 24 次首题请求当成 24 场完整面试，或把 1/1 报告成功称为稳定报告成功率。

## 1. 首题实验：做了什么、测到什么

固定[6 个合成输入](current-first-question/cases.json)，覆盖中级 Java 后端的 MySQL、Redis、线程池、库存项目、协作行为 5 类，以及中级 Python 后端的 asyncio 1 类。每例同一 DeepSeek 模型请求思考/非思考两种配置，各重复两次，交替顺序；2 次预热不计入统计。调用真实模型与 embedding、本机 HTTP、H2、内存 Lucene。**测试配置 `src/test/resources/application.yml` 将 `agent-enabled` 设为 `false`，所以这 24 次走旧首题路径，不能当成动态 Agent 的 24 次质量测量。** 执行命令：

```powershell
.\mvnw.cmd test "-Dtest=InterviewMeasurementTest" "-Dmeasurement.live=true"
```

本次原始文件：[运行日志](current-first-question/run.log)、[逐请求记录](current-first-question/samples.jsonl)、[汇总](current-first-question/summary.json)、[环境清单](current-first-question/manifest.json)、[隐藏配置标签的题目](current-first-question/quality-blind.json)、[配置映射](current-first-question/quality-key.json)。用量来自逐请求 `totalTokens`，不是厂商账单。

| 指标 | 全部 24 次 | 请求思考 12 次 | 请求非思考 12 次 |
|---|---:|---:|---:|
| HTTP 200 且首题非空 | 24/24 | 12/12 | 12/12 |
| 首题 API 平均耗时 | **1337.5 ms** | 1378.4 ms | 1296.5 ms |
| 首题 API P50 | 1352.6 ms | 1420.0 ms | 1318.2 ms |
| 首题 API P95 | **1918.8 ms** | 2101.8 ms | 1664.5 ms |
| 报告的对话 token 合计 | **12195** | 6321 | 5874 |

平均值是正式请求 `apiMs` 的算术平均；P50/P95 是排序后 nearest-rank (`ceil(p×n)`)。每组只有 12 次，组内 P95 就是该组最大值，不能当线上服务等级。响应时间包括本机 HTTP 至完整首题，不是首 token 时间，也不包括完整面试和报告。总 token 不包括全部准备语料的 embedding 用量。

**质量的探索性人工复核**：对[24 道匿名题](current-first-question/quality-blind.json)逐题检查其是否命中该案例事先写好的 `focus`；本助手判定 **23/24** 命中，Q11（MySQL 案例问 Spring `@Transactional` 失效）偏离该例指定的 InnoDB 隔离/MVCC/索引重点。这只是“首题目标考点命中”，**不是整场 JD 必考点覆盖率**，也不是独立人工盲评。Q01 把未提供的“线上发现并处理”当作经历、Q03/Q14/Q22 引入未经确认的线上线程池语气等，说明相关性命中也不能代表事实约束合格。未对 24 题做独立、预注册的多评委质量评分，因此不报告本轮“质量达标率”。

**实验有效性问题**：`InterviewMeasurementTest` 在 24 条请求及文件保存后，最终断言“同案例成对 prompt SHA-256 相同”失败。5/6 案例满足，行为案例 4 次请求出现 2 个 prompt hash，具体见[逐请求记录](current-first-question/samples.json)。这意味着本轮 A/B 的行为题输入不完全一致；不能把两配置的质量差异归因于思考开关。所有 24 次实际响应和延迟仍可作为这次观察值；测试总体状态必须写 **BUILD FAILURE / 1 项断言失败**，不能只报 24/24 成功。提示词漂移原因尚未定位，本次没有修改测试或业务代码去消除它。

## 2. 动态 Agent：真实案例与报告

先运行了单案例冒烟测试：[原始 JSON](agent-live-smoke-2026-11-03.json)和[构建日志](agent-live-retry-2026-11-03.log)。Python 初级岗位、合成简历、主问题上限 1。首题问 asyncio 调度；候选人答“不熟悉”；Agent 追问实际写过的代码，追问未作答后测试主动结束并生成报告。

- 自动测试：**1/1 通过**，报告 **1/1 生成**；这不是完整用户交互的报告成功率。
- 输出：两道题，其中一题已答、一题未答；未答题在报告中为 `score:null`。
- 用量流水：**5 次模型调用、11196 token**；决策元数据记录工具调用 **0 次**。本例没有验证真实模型主动检索。
- 人工复核：追问转向本人贡献，没有反复要求解释同一机制；报告未补造线上量级，且说明任务取消等未评估。但首题措辞预设候选人确实使用 asyncio 创建任务，简历只说异步报表练习，这是轻微证据前提问题。复核者仍是本助手，不能用作独立人工评分一致性结论。
- 日志总耗时 **57.131 秒**、测试用时 **49.64 秒**，均含启动与构建/收尾，不是面试 API 响应时间。

随后新增仅在 `-Dagent.eval.live=true` 时运行的 [AgentEvaluationLiveTest](../../../src/test/java/com/bupt/mockinterview/agent/AgentEvaluationLiveTest.java)，使用真实 DeepSeek、隔离 H2/内存索引，对 Python 初级技术题、Java 中级项目题、Java 中级行为题各运行一场。每场固定合成 JD/简历、回答一题、允许 Agent 作下一步决策、随后手动结束并生成报告。命令：

```powershell
.\mvnw.cmd test "-Dtest=AgentEvaluationLiveTest" "-Dagent.eval.live=true"
```

[原始逐场 JSON](agent-three-cases-2026-11-03.json)与[运行日志](agent-three-cases-run.log)已保存。测试 **1 项通过、0 失败**；三场均有有效报告。下表时间由测试中 `System.nanoTime` 量出，不含页面渲染/公网往返；“总耗时”含建本场测试资料、模型调用和手动结束报告，不是生产用户完整面试耗时。

| 场景 | 首题 ms | 回答至下一步 ms | 结束/报告 ms | 本场总 ms | 模型调用 | token |
|---|---:|---:|---:|---:|---:|---:|
| Python 初级·明确不会 | 2653.4 | 6084.2 | 14953.5 | 23718.3 | 4 | 8739 |
| Java 中级·项目贡献含糊 | 1746.6 | 5081.4 | 11553.8 | 18401.9 | 4 | 7820 |
| Java 中级·行为行动含糊 | 1780.0 | 5425.4 | 24682.3 | 31907.7 | 4 | 10372 |
| **平均（n=3）** | **2060.0** | 5530.3 | 17063.2 | **24676.0** | **4.0** | **8977** |

三场首题 P95 = **2653.4 ms**，总耗时 P95 = **31907.7 ms**；n=3 时 P95 都是最大值，**不能作为稳定 P95 或线上承诺**。总计 **3/3 报告生成、12 次调用、26931 token**。三场均出现有目的的追问，未答追问在报告中均保留 `score:null`；但是由于测试只回答首题，不能宣称完整多轮覆盖。

人工复核的**明确质量缺陷**：Java 行为场报告 `overallNotes` 写了“按前端方向复盘；JD文本为Java后端，方向不一致”，但输入 JD 明确是 Java 后端，资料中的“前端同学”只是协作对象。此为报告误读上下文，原句和输入均可在逐场 JSON 核对。Python 技术场的追问“你们当时的代码或流程是怎么处理的”也带未确认的实现前提，应先询问是否处理过；项目场追问本人写的 SQL 与思路来源，目标较明确。这些是本助手对三例的定性复核，**没有独立评审与人工评分一致率**。

## 3. RAG：本次重跑与正确解读

执行 ` .\mvnw.cmd test "-Dtest=RunEval" `，使用真实 DashScope embedding 和 Lucene 内存索引。[原始日志](rag-run.log)显示 **1 项通过、0 失败**。评测数据构造方式是 15 个主题，每主题 1 篇目标文档加 9 篇同主题干扰文档，每主题 2 条查询，共 150 篇/30 查询；目标文档 ID 是已知 ground truth。

| 方法 | Recall@5 | MRR@10 |
|---|---:|---:|
| 纯向量 | **96.7%**（29/30） | 0.825 |
| BM25 | 86.7%（26/30） | 0.700 |
| RRF 混合 | **96.7%**（29/30） | 0.825 |

入库 150 篇约 **19.872 秒**；单次 embedding 均值 **127.7 ms**、P95 **163 ms**，来自测试日志。检索纯阶段日志先取整毫秒，出现 0 ms P95 不能理解为无耗时。生产 `RagService.retrieve` 当前仍用用户过滤的**纯向量**检索，RRF/BM25 仅为这次对照，并未自动上线。

**RAG 精准率仍未测**：现有 ground truth 只标定每次查询的单篇目标文档，不代表其余 9 篇都不相关，因此不能拿“命中 29 篇 / 返回 150 条”算 Precision@5。下一次要从实际用途抽样查询（如“找候选人库存扣减的个人贡献”），由人逐条标注 top-5 为相关/部分相关/不相关和所属用户/资料版本，再算 Precision@5、nDCG@5、无关块率与越权块率。保留查询、命中 ID、原文片段和评分依据；再看这些证据是否真的被 Agent 正确引用。检索命中与最终答案正确是两项测试。

## 5. 如何在新场景复现并判断“优化后变好”

1. **写案例与分层**：固定 JD、职级、所选资料、回答轨迹和必考点；分别计独立案例与重复请求。v2 的 12 例是设计池，需逐例运行才变成实测样本。
2. **预定指标**：覆盖率 = 被有效考察的必考点 / 事先列出的必考点；报告成功率 = 有真实有效报告的完整场次 / 所有尝试结束的场次；恢复成功率 = 故障后在约定时限内恢复到有效状态的场次 / 注入故障场次。失败、未触发和 `null` 分分别记，不能混成 0 分或从分母删掉。
3. **保留原始运行**：输入版本/hash、模型与配置、问题/回答/报告、检索 ID、调用次数/token、每阶段时间、错误和重试；发布统计之前先检查配对输入 hash。本轮行为题漂移就是反例。
4. **独立评分**：被测 Critic 的分数只作输出。两名不知 A/B 标签的评审者按相同 rubric 独立给问题、追问、评分、报告标注；保留分歧并裁决。可报告人工一致率、模型分数对人工的平均绝对误差和分档一致率。另一模型作裁判也需先在人标样本上校准。
5. **成对对照**：同一案例、模型、预算和回答轨迹，只改一个变量；交错运行并记录每例前后差值。预先设定主指标及不能退化的红线（如无依据经历、越权证据），同时报告 token、成本和延迟。没有同口径基线时只说“建立基线”，不说“提升了百分之几”。

所有新数据仅来自本地隔离运行；未操作线上站点，未修改生产代码、模型配置或对外 API。
