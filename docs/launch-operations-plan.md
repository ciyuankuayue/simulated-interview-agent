# 试推广：账号配置、积分与运营方案

日期：2026-10-30。用户已确认本文主体页面与接口方案，并修正余额仅在账号页显示；反馈奖励机制及最终四题问卷已获确认。本文为本轮实施基线；具体交付与验证见docs/handoff.md。

## 1. 用户端

- 保留现有视觉与导航，“账号与设置”改为“我的账号”，内部三个页签：账号与积分 / 模型与 API / 使用记录。管理员额外看到“运营管理”。
- 账号与积分：账号及复制按钮、剩余积分、联系补额、补额记录；不把 API 配置作为开始练习的前置条件。
- 余额仅在账号页显示，移除全站页头余额；其他页面不显示积分数字，额度不足时仍按需提示。
- 模型与 API：先选择 DeepSeek / 通义千问；DeepSeek 下选择平台提供 / 我的 DeepSeek API。千问仅显示平台提供，Key 配置不出现在千问区域。
- 设置采用草稿与显式保存，保存前展示最终有效组合；切换到千问时草稿明确转平台模式并说明，提交同时发送 chatProvider=QWEN、keyMode=PLATFORM。保留已存 DeepSeek Key，但不暗中启用；切回 DeepSeek 默认平台，用户可主动选自己的 Key。
- 三种有效组合：平台 DeepSeek、平台千问、自带 DeepSeek。历史 QWEN+BYOK 配置按实际平台方式呈现，不回显为自带 Key 已启用。
- DeepSeek Key：未配置 / 已保存末四位 / 当前使用中；提供配置、更换、删除；保存按钮明确“保存并使用 DeepSeek API”。只有 Key 确实保存且设置成功，才显示已启用；部分失败显示真实已保存但未启用状态。
- 删除 Key 继续遵循既有回退平台契约，操作前说明影响。
- 面试开始区显示轻量状态，如“DeepSeek · 平台提供”或“DeepSeek · 我的 API”，点击进入模型设置；不在每条回答附加扣费提示。

## 2. 收费说明与结算

- 不逐轮弹窗、不逐轮提示消耗。余额仅在账号页显示，使用记录随时可查；余额不足才弹阻断提示。恢复失败请求仍需说明可能产生新用量。
- 配置 Key 的输入框下方、启用按钮上方放可读小字：模型费用由自己的 DeepSeek 账户支付；平台另按模型用量收服务积分；每 5,000 token 扣 1 积分；资料向量化另按平台积分计算。小字采用正常对比度，不默认折叠。
- 平台维持每 500 token 扣 1 积分；自带 DeepSeek 对话按总用量的 10% 换算 token 当量结算。舍入在内部 token 当量上处理，不按整数积分向上取整。
- 新旧规则按部署生效时间分界，历史流水与余额不回算；流水保留真实 token、计费版本、应扣和实扣。不足时现有 clamp 造成的减免独立反映，不能用应扣替代实扣展示。
- 自带 Key 不再调用前固定扣服务费；统一预检、取得用量后结算。同一调用通过唯一调用编号防重复结算；部分流式失败有可信用量则结算，其他情况保留估算/失败标识。
- 赠送 200 积分作为首批受控试推广参数，存量余额不自动重置；页面读取后端规则，避免赠送数、费率散落硬编码。9.9 元 / 1,000 积分为后续定价试验，不自动上线收款。

## 3. 运营管理（本轮实现范围）

| 页面 | 首版内容 |
|---|---|
| 概览 | 新注册、活跃、开始面试、生成报告、报告查看、积分消耗、平台估算成本、付费补额金额 |
| 用户 | 搜索账号，注册/最近活跃时间，模型与实际计费方式，余额、近7日用量、面试/报告数量 |
| 用户详情 | 用量流水、有限事件时间线、补额历史、补积分入口；不展示简历、回答、陪聊原文或 Key |
| 补额记录 | 赠送/付费/补偿/调整分类，积分、金额（仅付费）、原因、外部订单参考、操作人、时间 |
| 产品分析 | 注册→开始面试→回答→报告生成→报告查看漏斗，模型/API 使用分布，失败码分布，次日/7日回访 |
| 成本 | 按日/模型/场景的 token、估算人民币、失败/重试消耗，单场成本中位数及 P90 |

- 补额：选择用户→查看余额→选择类型和积分→填写原因→预览→确认。服务端唯一请求号防双击/超时重试重复加额；额度增加与补额记录同事务。已成功记录只追加补偿，不覆盖原记录。
- 人工确认收款才记录“付费”；赠送和补偿不计收入。记录金额不代表系统核验过支付，不把它算作利润。
- 默认今天/近7天/近30天筛选与分页，不引入外部分析平台、支付系统或独立管理站。
- 管理员跨用户查询和补额沿用 TenantContext.runAsRoot 特权边界，明细显式 userId/tenantId；全站汇总按受控租户范围聚合，不暴露通用任意查询。

## 4. 行为与指标口径

- 服务端事实：注册/登录成功、资料导入成功、面试开始/回答保存/报告生成、模型调用完成/失败、额度不足、配置保存、补额成功。业务结果提交后才算成功，不因遥测失败让用户主流程失败。
- 前端事件：允许页面的访问、练习入口点击、模型/API 配置打开、报告打开、反馈提交。事件携带唯一 eventId，允许重复上报但不重复计数；客户端“成功”不替代服务端事实。
- 字段白名单：用户ID（服务端从 JWT 绑定）、访问会话ID、事件名、时间、页面枚举、业务场次ID、模型/实际模式、耗时、结果/错误码、移动/桌面类别、受控推广来源码。拒绝任意 JSON、完整URL/query、输入框内容；来源码不关联第三方身份。
- 不采集 Key、JWT、密码、简历/JD/回答/聊天正文，不记录键盘和屏幕录像，不采设备指纹；管理员查看元数据，不新增浏览私密内容能力。
- 前端产品分析提供说明与关闭开关；关闭后停止可选前端事件，不影响必要的计费、安全和业务记录。原始产品事件保留90天后清理；首版只做滚动窗口统计，长期匿名汇总留待有需要再建设。
- 活跃用户=当日至少一次核心业务操作成功的去重账号；页面访问另列。开始面试=成功创建业务场次；报告生成和报告查看分开。
- 完成漏斗按注册用户队列及观察窗统计；次日/7日回访只计算已经走完观察窗的队列。推广来源若未保存到注册流程，不声称能关联获客效果。
- 离开页面不推断放弃原因；只标记观察窗内未继续，结合简短自愿反馈。反馈采用第8节已确认的四题问卷；用户提交前告知内容会由开发者查看。

## 5. 成本与限制

- LLM 使用流水增加调用编号及业务场次关联，记录真实 token、实际付费方、结算结果；失败与重试也要能关联。历史无场次的数据标记未归因，不强行拼成整场成本。
- 平台成本只计平台支付的调用，自带 DeepSeek 的模型费用单列为用户承担；其向量化仍属平台成本。缺少缓存/时段数据时显示保守估算，不称实际账单。
- 价格表按模型与生效时间版本化；成本估算与用户积分费率分离。
- 注册和登录限速、同账号模型请求并发限制、资料大小与累计量限制、单次模型输出与循环预算；复用现有 Redis/业务 guard，不引入新中间件。
- 平台日预算保护结合在途请求预留，达到阈值停止新平台付费调用，说明在途可能继续结算，不能把事后计数冒充硬上限。自带 Key 的平台向量化仍受该预算约束。
- 完整测量至少10场受控合成/获同意脱敏案例，覆盖两家平台模型、自带 DeepSeek、短长资料、报告、失败恢复；统计导入和整场成本，禁止以测试通过等同市场效果。

## 6. 已确认的主体接口增量

既有 settings、api-key、quota、usage 响应保持兼容；以下主体接口增量已获用户确认，实施时更新 docs/api.md，已按实现更新为现行契约。反馈奖励审核接口随第8节一并实施。

| 接口 | 用途与边界 |
|---|---|
| GET /api/user/billing-policy | 赠送积分、平台/BYOK费率、规则版本，页面统一读取 |
| GET /api/user/grants | 本人分页补额记录，只回用户可见字段 |
| GET/PUT /api/user/analytics-preference | 查看/修改可选产品分析开关 |
| POST /api/product-events/batch | 已登录用户、白名单、有界批次、去重、限速 |
| POST /api/feedback | 已登录用户、自愿四题反馈、有界长度、限速 |
| GET /api/admin/overview | 受限时间窗、聚合指标和成本估算 |
| GET /api/admin/users | 分页搜索与用户经营元数据 |
| GET /api/admin/users/{id}/activity | 单用户有界用量/事件明细，不返回私密正文 |
| GET /api/admin/grants | 补额记录分页筛选 |
| POST /api/admin/grants | 用户、积分、类型、原因、金额/订单参考、唯一请求号；返回补额与余额 |
| GET /api/admin/analytics | 漏斗、回访、来源与模型使用分布 |
| GET /api/admin/feedback | 分页查看用户主动提交反馈 |

- 全部 admin 路径服务端校验 ADMIN；普通用户403、匿名401，前端隐藏入口仅是展示控制。
- 原 POST /api/admin/quota 保留参数/响应，内部接入同一补额服务并记录 LEGACY 来源；由于旧客户端无唯一请求号，不宣称其具备新接口的请求幂等能力。
- 新增运营/行为表通过 Flyway 后续版本，沿用现有 owner 表隔离方式；不在本轮额外引入数据仓库。

## 7. 实现与验收顺序

1. 先落地补额账本、管理查询与页面、权限/租户/重复补额测试。
2. 再改用户配置页、按用量服务费、可读规则与历史兼容；验证三种组合及 Key 部分失败。
3. 再补有限行为事件、漏斗/反馈、成本归因与预算保护；验证关闭可选采集、恶意属性过滤和重复事件。
4. 最后完成完整场景测量、移动端与管理端检查、mvnw测试和打包；人审，不自动commit/部署。生产迁移先备份。

## 8. 已确认反馈奖励机制

- 产品内自愿填写短反馈，人工审核后一次赠200积分；账号页常驻入口，首次报告查看后显示一次非模态邀请卡，额度不足时提供可选反馈入口。不在面试/生成过程中自动弹问卷，不把反馈作为继续使用或正常补额的必经条件。
- 用户主动点击才打开表单；不要求加微信，不重新填写已知账号/模型等元数据，不要求提供简历原文或截图。
- 表单首版：本次体验结果（完成/中断/未开始）及所属功能；一条必填具体经历（哪里有帮助、卡住或不符合预期）；继续使用的主要障碍多选题（NONE/UNSURE互斥）；第4题平台建议选填；可选深入沟通联系方式。措辞中立，允许没有问题、不确定和暂不需要。
- 邀请与提交前说明：首次有效体验反馈审核后赠200积分，好评差评同等；每账号一次；预计48小时内处理（仅在开发者能承诺时采用）。表单不声称提交即到账。
- 有效标准：来自一次实际尝试、能对应具体步骤/结果/预期，不是复制灌水或重复领赠；不按字数、正面评价或是否接受建议判断。合理短评可通过；报错导致未完成体验也可获赠，不要求必须生成报告。
- 已知边界：每账号一次不能阻止多账号；配合注册限速、首批人数/奖励总预算及人工核验，不使用设备指纹。暂不做AI自动判有效。
- 后台反馈状态：待处理/已奖励/待补充/已关闭；“通过并赠200积分”单事务写审核和关联补额账本，唯一反馈ID防重复奖励；待补充显示具体缺失信息，保留原反馈。不自动将已关闭差评排除出产品分析。
- 提交后显示已收到、状态与预计处理时间；到账在账号补额记录可查。联系方式自愿填写，只用于本次反馈跟进，不默认添加为营销名单。
- 深访作为补充：每周可从愿意沟通的人里人工选择少量用户，用微信/问卷追问具体经历；不要求所有人走人工联系流程。
- 指标：邀请曝光→打开→提交→有效奖励，按完成/失败、平台/BYOK分组，结合自然使用行为判断。受奖励反馈并非全体用户代表，未返回用户也可能不填写，不能仅以问卷好评或付费意向证明留存/转化。
- 本人可查询/补充反馈，ADMIN审核；反馈文本保留180天、联系信息90天、产品事件90天，奖励标记继续保留防重。
